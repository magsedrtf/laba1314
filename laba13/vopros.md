## 1. Результаты выполнения

При запуске скрипта на экране появляется стандартное диалоговое окно Windows (MessageBox) с текстом:
> «Сообщение вызвано через прямой адрес из Таблицы Экспорта!»  
> Заголовок: «Системное программирование»

## 2. Исследование ASLR (таблица адресов)

| Номер запуска | Базовый адрес HMODULE (ОЗУ) | Виртуальный адрес функции MessageBoxW |
|---------------|-----------------------------|---------------------------------------|
| Запуск №1     | 0x7ffff0990000              | 0x7ffff09f0d30                        |
| Запуск №2     | 0x7ffff0990000              | 0x7ffff09f0d30                        |
| Запуск №3     | 0x7ffff0990000              | 0x7ffff09f0d30                        |
| Запуск №4     | 0x7ffff0990000              | 0x7ffff09f0d30                        |

**Наблюдение:**  
Адреса не изменялись между запусками. Это объясняется тем, что `user32.dll` является системной библиотекой и уже загружена в адресное пространство процесса. Вызов `LoadLibraryW` в данном случае лишь увеличивает счётчик ссылок и возвращает уже существующий базовый адрес. Полноценная рандомизация базовых адресов системных DLL (ASLR) происходит при перезагрузке операционной системы, а не при каждом запуске пользовательской программы.

## 3. Ответы на контрольные вопросы

### Вопрос 1
**Что физически представляет собой дескриптор HMODULE, возвращаемый функцией LoadLibraryW? С какого элемента (заголовка) PE-файла начинается этот адрес в виртуальной памяти?**

HMODULE — это базовый виртуальный адрес, по которому DLL спроецирована в адресное пространство процесса.  
Фактически это указатель на начало загруженного модуля. По этому адресу в памяти начинается **DOS-заголовок** PE-файла (сигнатура `MZ`), за которым следует PE-заголовок (сигнатура `PE\0\0`), COFF-заголовок и Optional Header. То есть HMODULE указывает на самый первый байт образа DLL в виртуальной памяти.

### Вопрос 2
**Опишите низкоуровневый смысл механизма ASLR. Какую проблему безопасности ядра операционной системы решает принудительное изменение адресов загрузки DLL при каждом новом старте процесса?**

ASLR (Address Space Layout Randomization) — механизм рандомизации адресного пространства.  
При запуске процесса (или при перезагрузке системы) операционная система загружает исполняемые модули, библиотеки, стек и кучу по случайным адресам.

Это решает проблему предсказуемости адресов. Без ASLR злоумышленник, знающий точный адрес нужной функции в DLL, может построить эксплойт (например, ROP-цепочку), который будет стабильно работать на всех машинах. При включённом ASLR адреса каждый раз другие, поэтому заранее подготовленный эксплойт перестаёт работать.

### Вопрос 3
**Почему функция GetProcAddress принимает имя искомой функции (MessageBoxW) строго в виде байтовой строки ASCII (b"..."), а не в виде стандартной Unicode-строки Python?**

В бинарном формате PE имена функций в **Таблице Экспорта** хранятся в кодировке ASCII (однобайтовые символы).  
`GetProcAddress` сравнивает переданную строку именно с этими ASCII-именами внутри DLL.  

Обычная Unicode-строка Python (`str`) в памяти представлена в UTF-16 (два байта на символ) и имеет другую структуру. Если передать её напрямую, сравнение не сработает, и функция не будет найдена. Поэтому имя обязательно передаётся как байтовая строка (`bytes` / `c_char_p`).

## Вывод

В ходе работы было освоено явное (динамическое) связывание с системной библиотекой Windows:
- библиотека загружается вручную через `LoadLibraryW`;
- адрес нужной функции получается через разбор Таблицы Экспорта (`GetProcAddress`);
- функция вызывается по найденному виртуальному адресу;
- после использования модуль выгружается через `FreeLibrary`.

Также исследовано поведение ASLR на примере системной DLL и получены ответы на контрольные вопросы.
